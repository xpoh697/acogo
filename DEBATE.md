### Archi
Коллеги, мы успешно скачали и препарировали приложение acoGO! 2.0 (`pl.aco.acogo` v1.9.0). Приложение оказалось на стеке Cordova/Angular, что позволило вытащить 100% чистый протокол без обфусцированного нативного кода.

Предлагаю архитектуру кастомного компонента `custom_components/acogo`:
1. **Ядро API (`api.py`)**: Асинхронный клиент на `aiohttp`. При старте/первой настройке клиент регистрирует устройство через `POST /listener/v1/device` с генерацией UUID `devId` и получает постоянный сессионный `devicePassword`. Все последующие вызовы идут с этими заголовками.
2. **Управление дверями и воротами (`lock.py` + `button.py`)**:
   - Главная дверь (замок 1): `orderId=ezOpen`.
   - Въездные ворота / калитка 2: `orderId=f2Open`.
   - Для открытия из режима покоя эмулируем родную цепочку приложения: `receiveCall` -> задержка 3 сек -> `ezOpen`/`f2Open` -> задержка 5 сек -> `endCall`. Если домофон уже звонит (`check-state` == `busy`), шлем команду напрямую без задержек.
3. **Мониторинг вызовов и сенсоры (`binary_sensor.py`)**:
   - Сенсор `Connectivity` (online/offline).
   - Сенсор `Ringing / Line Active`: опрос `POST /device/check-state` через `DataUpdateCoordinator`. Когда возвращается `"busy"`, активируем событие входящего звонка в HA.
4. **Камера (`camera.py`)**:
   - Вызов `POST /preview/request` с `previewType="video-only"` возвращает временные AWS STS credentials и Kinesis Video Streams WebRTC Signaling Channel ARN (`kinesisvideo.eu-west-2.amazonaws.com`).
   - В HA создаем сущность `camera`, отдающую snapshot и WebRTC-поток.
5. **Конфигурация (`config_flow.py`)**: Удобный UI-визард ввода email и пароля от портала myAco / acoGO с автогенерацией `devId` и сохранением сессии.

### Skeptic
Идея выглядит бодро, но в продакшене без доработок она положит домофонную систему дома. Вот 3 критические проблемы решения Archi:

1. **Race Conditions и блокировка физической шины домофона при открытии дверей**:
   Цепочка `receiveCall` -> `sleep(3)` -> `ezOpen` -> `sleep(5)` -> `endCall` занимает более 8 секунд. Если пользователь нажмет кнопку дважды, или сработает автоматизация, два параллельных корутина перехватят управление. Хуже того, если корутин будет прерван (например, перезапуск HA или отмена таски), запрос `endCall` не уйдет! Линия домофона останется в состоянии `busy`, блокируя звонки и физические трубки во всем подъезде/доме.
   *Требование*: Обязательный `asyncio.Lock` на каждое устройство и блок `try...finally: await self.async_end_call()` с гарантированным освобождением линии при любых исключениях и отменах задач.

2. **Утечка сессий видеотрансляции и лимитов AWS KVS (`preview/request`)**:
   Запрос превью переводит вызывную панель в активный режим стриминга видео. Если в HA открыть дашборд и не послать `POST /preview/end`, панель останется занятой и перестанет принимать звонки от гостей на улице.
   *Требование*: Жесткий тайм-аут жизни сессии превью (auto-timeout, например 30 секунд), контекстный менеджер управления жизненным циклом потока и вызов `POST /preview/end` при закрытии стрима или остановке интеграции.

3. **Сбои авторизации и отсутствие авто-восстановления сессии (Silent Auth Drops)**:
   Облако ACO может в любой момент инвалидировать `devicePassword` (ротация ключей на бэкенде, сброс сессий). Если интеграция встретит `401 Unauthorized`, сущности станут `unavailable`. Пользователю придется вручную удалять и заново настраивать интеграцию.
   *Требование*: Автоматический перехват 401 ошибки в `api.py` с прозрачной перерегистрацией устройства (`re-authenticate`), обновлением `devicePassword` в `config_entry` и повтором запроса. Также обязательное маскирование паролей в логах.

### Итерация 2: Доработка Archi
Полностью принимаю критику Skeptic. Вносим ключевые инженерные улучшения:
1. Для каждого домофона внедряем `device_lock = asyncio.Lock()`. Весь вызов оборачиваем в:
   ```python
   async with self._device_lock:
       try:
           if not is_busy:
               await self.api.send_order(dev_id, "receiveCall")
               await asyncio.sleep(3)
           await self.api.send_order(dev_id, "ezOpen" if door == 1 else "f2Open")
           if not is_busy:
               await asyncio.sleep(5)
       finally:
           if not is_busy:
               await self.api.send_order(dev_id, "endCall")
   ```
   Это на 100% гарантирует отправку `endCall` даже при сбое или отмене корутина.
2. Для `camera.py` делаем сессионный трекер: сессия стартует по требованию, снабжается `asyncio.TimerHandle` на 30 секунд неактивности, по истечении которого автоматически отправляется `POST /preview/end`. При выгрузке платформы (`async_will_remove_from_hass`) сессия принудительно гасится.
3. В `api.py` реализуем декоратор/метод с автоматическим перехватом HTTP 401: при получении 401 клиент вызывает `register_device` с сохраненными учетными данными пользователя, сохраняет новый `devicePassword` в `hass.config_entries`, и повторяет исходный запрос. Все пароли исключены из `repr` и debug-логов.

Идея отличная, но без учета нюансов реальной работы HA и Telegram бот сломается или создаст дыру в безопасности:

1. **Кэширование изображений Telegram и гонки файловой системы (File I/O Race & Stale Cache)**:

   - В `__init__.py` при вызове `async_setup_entry` сразу вызывается `coordinator.start_line_monitor()`.
   - В `coordinator.py` метод `start_line_monitor` выполняет:
     `self._line_monitor_task = self.hass.async_create_task(self._async_line_monitor_loop())`
   - Метод `_async_line_monitor_loop()` представляет собой бесконечный опросный цикл `while True:` с интервалом 3 секунды.
   - Метод ядра Home Assistant `hass.async_create_task` регистрирует корутину в общем реестре задач ядра `hass._tasks`.
   - Сразу после инициализации интеграций ядро Home Assistant вызывает барьер синхронизации: `await hass.async_block_till_done()`.
   - `async_block_till_done` ожидает завершения всех задач в `hass._tasks` (`while self._tasks: await asyncio.gather(*self._tasks)`). Так как цикл `_async_line_monitor_loop` бесконечен, он никогда не завершается!
   - В ядре Home Assistant срабатывает встроенный защитный сторожевой таймер стадии запуска (Stage 1 / Setup timeout), который ждет завершения фоновых задач ровно 10 минут (600 секунд)! Все это время веб-интерфейс отображает уведомление «Завершение запуска. Пока что не всё будет доступно». И только по истечении 10 минут ядро принудительно отпускает стадию запуска.

2. **Зависание pip-инсталлятора Home Assistant на `requirements: ["pillow", "aiortc"]` в `manifest.json`**:
   - В коммите `fe823cd` в `manifest.json` были добавлены зависимости `pillow` и `aiortc`.
   - При старте Home Assistant менеджер зависимостей `homeassistant.requirements` синхронно через экзекьютор запускает команду `pip install` для пакетов из манифеста с дефолтным таймаутом 600 секунд (10 минут!).
   - Пакет `aiortc` требует сборки и компиляции тяжелых C-расширений (`av` / FFmpeg, `cryptography`, `pylibsrtp`, `aioice`). В Docker-контейнере или на слабых процессорах (Raspberry Pi, x86 mini-PC) установка `aiortc` через pip зависает на компиляции CFFI/PyAV или упирается в таймаут pip (600 секунд = 10 минут).
   - При этом `aiortc` вообще не нужен на стороне сервера Home Assistant!
     - Видеотрансляция WebRTC воспроизводится на стороне клиента — в веб-браузере на Lovelace-карточке `acogo-webrtc-card.js`, используя нативный движок WebRTC браузера.
